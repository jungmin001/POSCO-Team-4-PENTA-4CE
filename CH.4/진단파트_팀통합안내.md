# 상태·원인 진단 파트: 팀 통합 안내

## 가져갈 파일

분석 실행에 필요한 Python 파일은 5개, 검증용은 2개로 총 7개다. 모든 경로는 CH.4 기준이다.

| 구분 | 파일 | 역할 |
|---|---|---|
| 필수 | Diagnosis.py | 실행 시작 파일. diagnosis.pipeline.main을 호출 |
| 필수 | diagnosis/__init__.py | diagnosis 폴더를 Python 패키지로 사용 |
| 필수 | diagnosis/features.py | 설비별 센서 선택, 과거 관측 요약, 진단 정답 시간 연결 |
| 필수 | diagnosis/model.py | 학습, 확률 보정, 판단 보류, 성능 평가, 관측 설명 |
| 필수 | diagnosis/pipeline.py | 데이터 읽기부터 학습·예측·보고서 저장까지 전체 순서 실행 |
| 검증용 | diagnosis/test_integrity.py | 미래 정보·정답 누수, 시간 경계, 7개 설비 입력 검사 |
| 검증용 | diagnosis/validate_results.py | 저장된 성능 재계산, 데이터 분할·확률 합·모델 추론 확인 |

함께 전달할 문서·환경 파일: diagnosis/README.md, requirements-diagnosis.txt, 이 안내서.

기존 Main.py와 src/의 전처리 코드는 이번 진단 분석에서 수정하지 않았다. diagnosis는 src를 import하지 않고 저장된 전처리 자료를 읽는다. 이전 대화의 대용량 C.csv 구조 점검은 별도 작업이며, 현재 진단 분석 실행에 필요한 파일은 위 목록이다.

## 폴더 구조 유지

```text
CH.4/
  Main.py                      기존 전처리 실행 파일
  src/                         기존 전처리 코드
  Diagnosis.py                 진단 분석 실행 파일
  requirements-diagnosis.txt
  diagnosis/
    __init__.py
    features.py
    model.py
    pipeline.py
    test_integrity.py
    validate_results.py
    README.md
  Data/
    Processed/Scenarios/        센서 입력
    Raw/                       manifest 및 학습·검증 진단 정답
  Results/Diagnosis/           결과 저장
```

features.py 등의 파일을 폴더 밖으로 각각 옮기면 상대 import가 깨질 수 있으므로 diagnosis 폴더를 통째로 유지한다. 기본 경로는 diagnosis 폴더의 부모인 CH.4 기준이다.

## 실행 순서

```text
Diagnosis.py
  → diagnosis/pipeline.py
      → features.py: 특징 생성 + Raw 진단 정답 연결
      → model.py: 상태·원인 학습 및 평가
      → pipeline.py: 예측·혼동 사례·그림·보고서 저장
```

팀 전체 파이프라인에서는 전처리 결과가 준비된 다음 진단 단계를 호출하면 된다. 학습은 매 화면 조회마다 수행할 작업이 아니다. 모델을 저장한 후 화면 연동 단계에서는 저장 모델 추론 경로를 사용한다.

## 명령어

CH.4 폴더에서 실행한다.

```powershell
# 전체 특징 생성·학습·평가·시험 예측
python Diagnosis.py

# 입력이 동일하면 특징 캐시 재사용. 모델 학습은 다시 수행함
python Diagnosis.py --reuse-features

# 저장 모델을 읽어 C 설비 한 시나리오 추론. 새로 학습하지 않음
python Diagnosis.py --predict-scenario S0289 --equipment C

# 모델을 재학습하지 않고 저장 결과로 보고서 재생성
python Diagnosis.py --report-only

# 코드 무결성 검사
python -m unittest diagnosis.test_integrity

# 전체 7개 설비 결과를 만든 뒤 결과 검증
python -m diagnosis.validate_results
```

팀 폴더가 다르면 --scenarios, --raw, --output으로 경로를 명시할 수 있다. 기존 팀 Main.py의 인자와 충돌하지 않도록 CLI는 별도 프로세스로 실행하는 방식이 단순하다. pipeline.main()은 명령행 인자를 읽는 함수이므로 아무 인자 처리 없이 팀 Main.py에서 직접 호출하지 않는다.

## 입력과 출력

| 구분 | 경로 | 설명 |
|---|---|---|
| 센서 입력 | Data/Processed/Scenarios/Sxxxx/A.csv 등 | 이미 전처리된 설비별 관측 |
| 학습 구분 | Data/Raw/manifest.json | 원래 train/validation/test 구분 |
| 정답 | Data/Raw/diagnostics/Sxxxx.csv | 상태·원인 학습과 평가에만 사용 |
| 저장 모델 | Results/Diagnosis/models/ | 설비별 state/cause joblib 모델, 보정값·기준·칼럼 정보 포함 |
| 화면 연동 예측 | Results/Diagnosis/predictions/*_dashboard_test.csv.gz | 시험 상황 전체의 상태·원인 후보·검토 필요 표시 |
| 작은 확인 표 | Results/Diagnosis/tables/*_latest_test.csv | 시험 상황별 마지막 관측만 저장 |
| 결과 설명 | Results/Diagnosis/먼저읽기_진단결과.md | 성능·한계 요약 |

GT_ 정답, 행 번호, 시나리오 번호, 경과 시간, IS_MAINTENANCE, IS_OUTLIER는 모델 입력에 사용하지 않는다. 추론 경로는 센서 허용 목록과 저장 모델을 사용하고 diagnostics 정답은 읽지 않는다. 현재 CLI는 경로 설정을 위해 Raw/manifest.json을 읽는다.

## Git과 화면 연동 주의사항

Results/Diagnosis/.gitignore는 features/, models/, predictions/를 제외한다. 이 폴더는 로컬에는 있지만 일반 git add/commit/push로 팀원에게 전달되지 않는다. 모델이 필요한 팀원에게 models 폴더를 별도로 전달하거나 동일 코드로 재학습해야 한다. features 캐시는 재계산할 수 있어 필수 전달물이 아니다.

화면에서는 state_prediction과 state_probability를 표시한다. cause_candidate/cause_candidate_2는 이상으로 판단된 경우의 후보다. needs_review 또는 cause_needs_review가 참이면 확정 진단 대신 추가 점검 필요를 표시한다. 원인 후보 점수는 이상 상태라는 조건 아래의 값이며 원인의 실제 발생 확률을 보장하지 않는다.

이번 모델은 첫 기준 모델이다. 특히 A·C·F 원인 진단은 현재 기준에서 모두 판단 보류하며, 고장 상태의 검증 사례가 매우 적다. 팀 통합 과정에서 이 제한을 제거하거나 높은 상태 점수를 원인 정확도로 바꾸어 설명하지 않는다.
